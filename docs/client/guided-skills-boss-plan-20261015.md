### 3.1 独立个人蒸馏流程

3. 引导多轮补充求职偏好、项目职责与证据、表达习惯和自动回复边界。区分已知与待补，不重复问已确认问题；可跳过、保存、取消和稍后继续。

6. 用户逐项编辑并确认，原子保存个人 Skill 的新版本，登记产物。未确认草稿不能被自动回复入口采用。
7. 访谈不限制总次数；确认当前结果后仍可随时对话补充或直接编辑，整理局部更新并逐项核对差异，保留用户手工内容、原始回答和旧确认版本。实际写出登记新版后告知，展示仍待确认项及旧引用；活动 Run 继续使用原快照，BOSS 显式选择采用版本。全面边界与先行设计见[持续访谈](continuous-profile-interview.md)。

- 2026-10-17用户明确：已配置的个人资料仓库也应默认作为个人Skill保存工作区，允许本人显式另选；不能由作者擅自换到客户端运行数据目录。当前实例已使用同仓库的两个逻辑绑定，公开包不携带个人路径；跨新实例的自动默认建议若需新增交互或协议，仍先Figma/通用契约再实施，不能在客户端写死业务资源名。
- Key 只存客户端受保护凭据库，工作区/Skill/模板仅保存逻辑绑定，不写明文 Key。全部模型 token 消耗由用户自己的 API Key 承担，覆盖蒸馏、试聊、JD 判断、自我介绍、聊天、模型辅助解析及流程生成/修改；不使用开发者 Key、共享额度或后台兜底模型，不静默更换服务/模型。无可用绑定则保留草稿并阻止该次模型调用，展示可取得的请求用量，未知用量不能填零。
- 个人事实、表达风格、流程动作授权分别管理；推断不能升级成经历，风格不能扩大可外发事实，Skill 不能授予发送权限。
- 修改产生新确认版本；流程显式选择采用版本。外部手改、摘要不一致、工作区移动/丢失、删除被引用版本时明确阻止或要求重新确认，不静默读最新版或清除引用。
- 模型每轮只接收用户允许的必要材料和当前会话。外部材料和招聘消息均为不可信内容，不能改变规则、请求其他文件或获取密钥。
- 公开模板默认不包含个人 Skill、真实简历、项目代码、聊天记录、工作区绝对路径或登录态；共享个人成果必须另有明确的选择与范围核对。

### 3.3 BOSS 模板与日常使用

- 完整本地业务路径从登录开始：打开用户指定入口 → 检测登录 → 用户扫码/验证码等必要接管 → 复验实际求职者账号 → 按条件自动投递 → 处理对方索要简历、自我介绍和会话。登录失效停止本批，不自动破解验证码或切换账号。
- 多入口分别负责配置/预检、筛选与投递、有限批次消息检查与回复、人工待办与结果复核；每个入口单独声明资源、动作和可定时性。
- 使用者在表单选择简历版本、个人 Skill 确认版本、AI 服务、浏览器与账号，并填写关键词、城市、薪资、排除条件、每轮/每日上限、时段和停止条件。
- 先只读核对实际网站入口与账号，再以“只生成草稿”试用；按问题类别选择禁止、需要确认或配置范围内自动。导入和选择 Skill 均不自动启动或授予权限。
- 对方主动沟通时先读取并关联该会话的真实 Job Description，核对岗位名称、职责、要求、公司/联系人及用户目标，保留来源与内容摘要，再判断是否回复。不能只凭招呼语、对方名称或 AI 猜测职责作决定；缺失、错绑或变化的 JD 先通知用户。
- 职位判断分三路：明确符合则进入已授权的简历/自我介绍/聊天；明确不符合则准备独立“不感兴趣”动作；模糊、证据不足或 AI 拿不准则保留原因和 JD 摘要，通知用户，不自行答应或拒绝。例如用户明确求职前端，对方 JD 明确招聘主播，归明确不符合；相近岗位或标题/职责矛盾不能简单按关键词拒绝。
- “不感兴趣”是可改变站点会话/推荐状态的独立副作用，必须声明动作、配置 deny/confirm/auto、绑定具体会话及 JD/规则版本、提交前复验、去重并核对页面回执。仅在当前真实页面提供且用户授权的入口执行；入口缺失、语义不清或结果未知转人工，不伪装点击或改用聊天拒绝代替该动作。
- 对方主动索要简历时，在会话身份、JD 适配和发送授权有效后，发送用户选定的简历版本；发送附件与发送自我介绍分别记录，不把“打招呼”记为简历已送达。明确不符合或待人工判断的会话不先发送简历。重复索要、已发送、附件版本变化和重新发送的意图分别处理，不因重复消息自动重复发送。
- 简历已确认事实通常一两句回答；未知经历转人工；普通技术交流限定已确认能力；正式面试/笔试/作业默认通知本人并可生成内部参考，不自动代交。薪资承诺、面试时间按预设范围处理，超范围转人工。
- 语气自然、简短、一致；阅读/处理节奏服务于实际任务，不以随机延迟冒充本人已读题。身份质疑默认暂停该会话并通知本人，或按用户确认的真实助手说明回复，不固定否认使用 AI。
- 生成后与发送前复验账号、目标、最新消息、简历/Skill 版本和授权；新消息、本人插入回复或规则变更使旧草稿/确认失效。
- 本人进入手动接管状态后立即阻止该会话新的自动发送，下一次发送仍须复验；不影响其他会话。恢复时读取最新对话并显式确认。不能凭检测不到站外人工消息就声称所有竞争发送已消除。
- 外发先持久化并去重，再执行和核对。明确显示草稿、待确认、已确认发送、失败或结果未知；未知不重放，不通过换驱动重试。日限额/去重跨 Run、计划与重启有效。
- 等待回复或等用户补充时持久化后释放执行槽；按分钟计划或显式运行处理有限批次。重启不补发旧消息。验证码、登录失效、账号变化、页面不匹配、资源失效或达到预算/上限时停止并建立可定位到具体会话的待办。
- 微信/电话交换沿用独立动作授权；实际读取对方微信后去重建立联系人与来源提醒，系统通知失败保留应用内待办，不自动添加好友。

### 3.4 AI 对话消息与顺序

2026-10-15 用户补充：AI 对话交互优先使用 `onmessage` 消息回调接收增量和状态，避免消息乱序。该要求覆盖个人蒸馏、试聊和通用 AI 对话；BOSS 外发仍沿用独立动作授权与提交核对。

- UI 通过宿主白名单事件订阅的 `onmessage` 接收标准化消息；Provider 流式传输由宿主适配，不把回调命名等同于必须采用 WebSocket，也不让 Renderer 持 Key 直连模型。新增消息格式先发布通用契约，当前0.18.0节点并未因此具备流式能力。
- 契约须关联会话、轮次、请求及尝试身份，提供稳定事件ID、单个请求流内的单调序号和明确的完成/失败/取消终态。各会话独立排序；UI 先核对身份，再按序归并消息。同一会话默认串行生成下一轮，重复提交幂等；允许的并发请求必须固定各自消息位置，不按完成先后插入对话。
- `onmessage` 进入每个请求的串行处理队列；异步解析、持久化和渲染不能因耗时不同覆盖新状态。重复事件去重，乱序分片仅作有界暂存，序号缺口超时或超界后停止拼接并核对宿主持久化快照，不能忽略缺口或假定收到完成事件就已收齐正文。
- 取消、超时、重试、切换会话和重新生成时使用请求身份及会话修订校验；旧请求的迟到分片、回执和错误不修改当前消息或确认结果。终态只能采纳一次，旧订阅必须解绑；手动重试使用新尝试身份，不混入上一次残片，不隐式再消耗token。
- 重连或重开先恢复已保存消息与最后连续游标，再按契约补齐事件或获取完整快照；恢复展示不重新调用模型，不重放外发。终态与最终内容持久化时核对预期会话修订，冲突保留用户输入并提示恢复，不覆盖手工修改。
- 流式正文属于未完成草稿，只有完整响应通过格式/事实及当前修订校验后才供后续节点或结果确认采用；部分文本、完成提示本身和显示顺序都不能成为外发授权。用量仍按用户Key和请求记录，未知用量不填零。

2026-10-18状态：持久完整快照onmessage与本地顺序归并、[迟到保存回执](conversation-receipt-order.md)、[流式身份核对](conversation-stream-identity.md)、[真实本机HTTP](conversation-connection-failure.md)和[原生IPC六场景](conversation-native-ipc.md)已有分层实现/人工证据。真实供应商、完整并发/期限/预算/进程与订阅生命周期及全部S08矩阵仍未完成；新增消息字段、游标或恢复协议继续先G1后G2，不以局部矩阵标记本节整体通过。
