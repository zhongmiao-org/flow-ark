## 已确认的实际状态

当前安装版为客户端 #229，源码核对至 #230。DeepSeek/deepseek-flash 的真实 API 调用、结构化补问及若干完整小流程生成有实际证据，但这些不等于自主 Agent 创建流程已经通过。

2026-10-12 在当前唯一原生 FlowArk 实例和独立核对资料中，输入“新建 BOSS 直聘投递简历流程，由 AI 自动选择技能、模板或 MCP，人工只 review / 微调”，明确仅生成，不投递或发消息。第一次实际响应为补问，询问职位、城市/筛选、动作范围、简历、数量和登录处理。用虚构的“Java后端、上海、在线简历、最多10个、异常停止、人工登录”补齐后，第二次实际响应仍为补问，要求人工先在宿主选择 BOSS 网页或勾选 MCP 工具；没有返回完整流程，没有采纳或创建新 Run。

源码依据：客户端 `src/ai/planning.ts:42` 明确“只规划，不执行，不调用工具”；`src/ai/providers.ts` 为结构化模型请求，没有规划期工具调用循环；`src/host/planning.ts` 仅向模型提供已选上下文/工具和通用节点能力；`src/host/task-mcp-targets.ts` 要求既有人工连接/工具选择。没有把本次未选工具等同于全机没有连接，也没有将模型说“没有技能”当作读取过技能目录的证据。

模板仓库 `templates/recruiting-boss/template.json` 只发布“适配状态检查”入口；`templates/recruiting/src/sites.ts` 的真实站点适配器尚未校准，投递等方法明确拒绝执行。已有招聘策略、去重和事实校验代码，不等于已有可直接使用的 BOSS 投递模板。不能用另一个客户端小流程、模拟网站、JSON 校验通过或连接成功替代 BOSS 投递验收。

## 用户应承担的操作

用户主要提供业务条件，核对 Agent 推荐的资源与影响，review 生成的步骤，必要时修改条件或文案，然后确认运行。登录、验证码、账号/简历选择、首次连接凭据与实际外发授权仍由用户明确处理；这些与逐节点配置 RPA 不同。已经提供的业务条件继续保留，不因能力发现失败重复询问。

Agent 负责查找可用能力、理解技能规程、选择候选、配置节点参数/数据引用、组装条件与循环、验证完整流程，并展示依赖、来源、缺口及外部影响。缺能力时说明具体缺什么、哪些部分不能使用及恢复入口，不能用占位节点、猜测选择器或假称工具已连接来交付“可直接用”。

## 后续实现边界与顺序

1. 定义通用的本地能力目录与候选来源契约，覆盖已安装技能/模板入口和已连接 MCP 定义；技能来源、版本、允许操作及引用方式独立定义。客户端不读取相邻仓库源码，也不自动下载技能、程序或依赖。BOSS 等业务知识、提示词、选择器和流程仍归独立模板仓库。
2. 定义受宿主管理的 Agent 规划工具循环。模型可请求查找目录、读取选定候选规程、校验流程；模型不自行持有凭据或系统对象。真实服务探测必须限定到用户核对过的对象与范围，并有宿主许可，不能只根据 MCP readOnlyHint 判定安全。轮数、耗时、取消和失败有边界；规划期不能投递、发消息或绕过执行确认。
3. Agent 推荐技能/模板/MCP 和对象，由用户 review 推荐范围，再自动生成完整的可校验流程及本地候选绑定。选择候选不授予执行权限；确认后使用不可变版本与每次运行授权。工具/网页组合不得绕过既有范围检查，所需新组合先定义契约，不简单删除旧限制。
4. 实现 BOSS 实际可用能力：真实账号/简历/职位及动作入口校准、筛选、去重、数量限制、外发确认、结果核对与未知停止。缺少这些时只报告缺口，不能把 AI 补问或业务探测模板称为可投递流程。
5. 用完整主路径核对人工工作量：除了业务补问、登录/对象确认、review/微调及执行确认，成功样例不需要人工拖节点、写选择器、选择具体技术工具或填 JSON。

页面沿用 [AI 任务体验](design-ai-task.md) 对应的开始、理解、方案、检查、结果与失败状态，继续采用 Figma 和 Ant Design；未覆盖的 Agent 发现/进度状态先补设计，再实施。协议、权限和持久化变化先更新治理契约，再更新客户端。当前阶段不新增或运行单元测试；类型检查、构建与人工真实核对分别记录。
