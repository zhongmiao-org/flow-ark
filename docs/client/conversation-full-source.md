# 聊天窗口与完整访谈来源

2026-10-17，用户在累计21次请求的持续访谈中看到“已选12/12”，指出范围含义不清。本次核对证实：12是作者配置的单次历史窗口默认值，21是总请求数；当前发送与来源确认都复用该选择，未选的早期对话虽保存在本机，却不进入模型消息和确认正文。这是完整个人蒸馏的实际缺口，不能以本机保存完整历史、最新回答的摘要或把窗口数字调大作为完整来源证据。

## 已核对的实现

客户端#297已安装，普通回复直接发送。conversation v2默认12、可配置1–24轮；`ConversationThreads.checkpointSource`调用与模型发送相同的`resolveConversationSelection`，并只把返回的问答放入transcript。0.32.0的固定确认保存完整历史尾摘要，但正文仍只有明确选择的轮次；尾摘要本身不能证明模型处理过全部历史。原个人0.5.2仍为旧会话来源流程，不因同ID关联持续会话就自动升级其蒸馏入口。旧输出、确认、Skill和Run保持原语义。

请求数包含失败、取消和显式重试，不能简单把总请求数当成完整问答数，也不能用“21减12”推断恰有9轮完整问答未覆盖。窗口仅选择完整成功问答，失败时本人的新输入仍可能包含重要补充，完整访谈不能将其一起丢掉。

## 产品与通用能力决策

1. 分别显示累计保存请求数、本次聊天发送的完整问答数及单轮预算。普通聊天可选查看实际范围；不要求逐条勾选。默认12是当前实现选择，并非用户设定或供应商强制上限。必要旧内容未在本次范围时不得声称模型已经记住或已发送全部历史。
2. 增加独立的完整访谈来源确认，覆盖固定时刻的原访谈、持续补充、各材料/设置来源、全部本人输入、完整回复及未完成状态。它与聊天窗口、Skill最终确认和外发授权分开；仅在本机固定来源，不调用模型。确认后可继续补充，旧来源不可变，新补充必须有新的固定来源。
3. 总历史不设12/24或固定总题数门槛。完整来源使用有界清单、不可变引用与分页读取，不把无限数组塞进head/onmessage/IPC或单次模型输入。绑定同会话、原始来源摘要、历史尾部、资料版本和顺序；跨页去重、缺页、摘要、终点与当前修订必须可核对。安全整数、单页字节、磁盘和执行预算仍有明确边界，超限停止而非静默截断。
4. 来源清单只表示已固定和可追溯，不能表示AI已整理或事实已确认。完整访谈分页后由作者在客户端可视化编排逐批整理、合并结构化草稿、展示冲突与未知，最后本人核对。客户端提供通用读取和覆盖校验；求职事实、偏好、措辞与动作规则归模板，不能写死招聘字段或使用一个大脚本替代可视化流程。
5. 整理以原始时间顺序处理，保留早期偏好、后续更正、撤回和来源归属。本人输入与助手建议分开；部分助手回答不成为完成结果。草稿的“已覆盖/总来源/未处理/失败”对应实际固定页和实际请求收据，模型自报“已全部总结”不作为覆盖证据。来源改变、缺页、处理失败或结果未知时不得标完整；已处理内容和手工修改保留，核对原请求后继续。
6. 每次整理使用本人绑定的Provider/model/受保护Key，显示分批范围及实际或未知token用量。来源确认、只读查看和重开不调用模型；恢复不自动重放已完成或结果未知的模型请求。费用意图与预算先可见，不因分页暗中增加后台付费总结。
7. 新版Skill发布必须具备完整来源与实际整理覆盖，以及最终编辑/试聊/本人确认。继续引用已确认旧Skill时准确标示其来源版本；不能以旧确认覆盖新补充。文件写出/读回/登记/成功告知与绑定显式采用仍按持续访谈完整边界分别实现。
