# 公共契约管理

此目录属于治理仓库，用于管理客户端、服务端和管理台共同理解的语言无关协议。

**当前仅有管理约定，没有机器可读 Schema、OpenAPI 文件、生成代码或已发布契约版本。** P1.1 建立本地流程与运行契约，P2/P3 再增加实际需要的平台协议。

## 契约分层

| 阶段 | 内容 | 载体与边界 |
| --- | --- | --- |
| P1.1 | 流程定义与版本、节点描述、运行请求/快照/事件、文件/凭据引用 | JSON Schema 和脱敏示例 |
| P1.1 | NodeExecutor、平台连接边界的职责 | 接口说明；函数与 AbortSignal 等运行对象不伪装成 JSON 数据 |
| P2 | 设备能力、注册、心跳、事件补报、管理查询 | OpenAPI、消息 Schema 和兼容示例 |
| P3 | 版本发布、授权、命令、回执、平台调度 | OpenAPI、消息 Schema 和去重/授权用例 |

本地 IPC 是客户端内部接口，由客户端维护和测试；需要跨进程传输的数据复用本目录的对应定义。不要为了“统一契约”把 Electron 专属接口暴露成平台 API。

## 唯一来源与消费者

- 治理仓库维护规范源文件和示例；React Flow 数据、Java DTO、TypeScript 类型、ORM 实体均不能成为另一个独立协议源。
- 采用 JSON Schema 2020-12 和 OpenAPI 3.1 作为初始规范方向；选择生成器时验证其实际兼容范围。不能把单端编译通过当成跨语言兼容证明。
- 每个契约发布包含版本化源文件、示例、变更与兼容说明、可核对的内容摘要，并对应不可变 Git tag。
- 初期消费者将某个已发布版本的规范及生成产物纳入自身仓库，记录来源版本、内容摘要、生成器版本和再生成命令；复制件只由发布版本更新，不手工分叉维护。
- 暂不搭建私有包注册中心。未来如改为包分发，仍固定契约版本，不使用相邻目录依赖或运行时读取主目录。
- 规范源仓库为 [zhongmiao-org/flow-ark](https://github.com/zhongmiao-org/flow-ark)。tag 名称与第一个契约版本在实际发布时记录；治理文档上传不等于契约已经发布。

## 版本与兼容

治理文档版本、契约版本、流程格式版本、节点类型版本和应用版本分别记录，不能用应用版本代替全部兼容判断。

- 契约使用语义化版本：破坏兼容为主版本，兼容扩展为次版本，文档或不改变语义的修正为补丁版本。
- 增加字段、枚举、节点或必填条件前，检查旧端解析与校验行为；不能假定所有新增项都兼容。
- 客户端声明支持的格式、节点和能力范围；遇到不支持的流程版本或必需能力，在执行前拒绝并说明原因。
- P2 建立设备能力与协议范围协商；P1 不实现无实际消费者的平台握手。
- 已发布流程版本不可变。协议迁移产生明确的新版本或迁移记录，不能静默改写已授权版本。

## 跨仓库变更顺序

1. 在治理仓库更新定义、示例、兼容说明及必要的迁移说明。
2. 验证正反例与旧版本行为；有 Java/TypeScript 消费者后，分别做解析和序列化往返验证。
3. 发布契约版本，再在受影响应用仓库中分别更新固定版本和生成产物。
4. 按兼容说明部署或发布消费者。需协调升级时记录支持范围与先后顺序。
5. 在各自仓库报告验证结果，不以治理仓库发布成功代替应用已兼容。

## 定义中不得携带的内容

- 明文密码、Token、浏览器 Cookie、系统凭据或 Profile。
- 活跃浏览器会话、函数、进程句柄等不可序列化运行对象。
- 把绝对本地路径当成服务端可以访问的文件；应使用有归属的 ArtifactRef。
- 真正业务账号、真实订单和客户数据；示例只使用虚构数据。

完整的所有权、执行语义和平台边界见 [总体架构](../docs/architecture.md)。
